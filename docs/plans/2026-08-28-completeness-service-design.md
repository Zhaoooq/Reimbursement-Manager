# Completeness Service and File Health Design

Tasks 15 and 16 introduce `CompletenessService.calculate(item_id)`. It returns an immutable `CompletenessResult` rather than storing completion percentage, `is_complete`, or missing counts in SQLite. The result contains `required_count`, `completed_count`, integer `percentage`, `is_complete`, and ordered `MissingMaterial` entries with the material type ID, stable code, and display name. This keeps material status derived from the Item's own MaterialRequirements plus files that actually exist now.

The service receives `DatabaseManager` and `StoragePathService`, with an injectable FileService. In one database transaction it eagerly loads the Item's requirements and lists all Attachments. Every attachment path is resolved from its stored relative path and checked through FileService. A regular file marks its Attachment `AttachmentHealth.OK`; an absent, non-file, or unsafe/unresolvable path marks it `AttachmentHealth.MISSING`. Changed health values are flushed in the same transaction, giving later pages a durable diagnostic state without treating it as the source of truth for completeness.

Only requirements where `required=True` contribute to the denominator. A requirement is satisfied when one or more associated Attachments have a present regular file. Extra attachments and optional requirements do not inflate counts. If two invoice files exist and one was manually deleted, the invoice is still complete as long as the other remains. No required requirements produces `0 / 0`, `100%`, and `is_complete=True`, so an intentionally empty template does not leave an Item permanently blocked.

StoragePathService path validation failures are treated as unavailable files instead of crashing the calculation. This is a defensive response to stale or manually altered attachment rows. Alternatives that trust Attachment rows alone or persist a percentage column were rejected because both become incorrect as soon as a user deletes a file outside the app. Tests cover 3/4, 4/4, external deletion and health persistence, recovery after file restoration, multiple attachments per material, an empty template, and missing Item errors.
