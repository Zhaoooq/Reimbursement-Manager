# Item Creation Design

Task 8 introduces `ItemService.create_item()` as the single application-layer transaction for creating an Item from a Template. The service receives the Batch ID, Template ID, sequence number, Item fields, and monetary values in integer cents. It validates user-controlled values, verifies that both parent records exist, and rejects a duplicate sequence number within the same Batch before creating any persistent data. New Items always begin in the reimbursement workflow state `COLLECTING`; material completeness remains dynamically calculated later and is not stored here.

The recommended design treats MaterialRequirements as part of the Item aggregate. `ItemRepository` gains a batch-and-sequence lookup, a child-requirement create operation, and an eager Item query that loads each requirement and its MaterialType. The service uses `TemplateRepository.get_by_id_with_materials()` to read a deterministic snapshot, creates the Item, then copies every TemplateMaterial's `material_type_id`, `required`, and `sort_order` into a new MaterialRequirement. The entire flow runs inside one `DatabaseManager.transaction()`, so a failure while copying any requirement rolls back both the Item and all requirements already flushed.

Two alternatives were rejected. Writing MaterialRequirement rows directly from the service would blur the Service/Repository boundary established by ADR-0002. A separate generic template-instantiation framework would add abstraction before another use case exists. The aggregate Repository extension is consistent with the existing Template/TemplateMaterial implementation and keeps this task local.

The copied requirements deliberately have no ongoing dependency on the Template. Later Template edits or deletions cannot change an existing Item's requirements. Returned Items eagerly load and sort requirements so callers can inspect the snapshot after the Session closes. Tests cover a full field copy, required/order preservation, snapshot independence after Template edits, missing parents, duplicate sequence numbers, input validation, and forced mid-copy failure with database rollback.
