# Database Models Design

Task 3 defines seven SQLAlchemy 2.x declarative models around the required business hierarchy: `ReimbursementBatch`, `Item`, `MaterialRequirement`, and `Attachment`, with `MaterialType`, `Template`, and `TemplateMaterial` supporting classification and initialization. Models are split by responsibility under `database/models`; a shared declarative `Base` and timestamp mixin prevent duplicated infrastructure. Workflow and attachment-health columns reuse the domain `StrEnum` values and configure SQLAlchemy to persist lowercase values rather than Python member names.

Money uses integer cents (`unit_price_cents`, `total_amount_cents`) with non-negative checks, avoiding floating-point rounding. Item sequence numbers are unique within a batch. Requirements and template materials are unique per parent/material pair. Attachment paths are globally unique, while duplicate file hashes are unique only within one Item, allowing the same invoice file content to belong to different Items. Searchable Item fields and foreign keys receive indexes. Every model has `created_at` and `updated_at` timestamps.

Deletion follows ADR-0001. Batch-to-Item, Item-to-Attachment, and MaterialType references use `RESTRICT`; the ORM does not silently null or delete those children. Material requirements and template materials contain no filesystem state, so they use database cascade and ORM delete-orphan semantics. Modifying a Template cannot affect existing Item requirements because `MaterialRequirement` stores no Template foreign key. Tests create temporary schemas only for model verification—production schema creation remains Alembic Task 4—and cover metadata, persistence codes, relationships, constraints, duplicate attachment scope, safe delete behavior, and timestamps.
