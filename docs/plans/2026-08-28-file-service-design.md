# File Service Design

Task 12 introduces `FileService` as the only low-level component that mutates attachment files and directories. It exposes `ensure_directory`, `file_exists`, `copy_file`, `move_file`, `delete_file`, and `transfer_file`. `transfer_file` defaults to `FileOperationMode.COPY`, preserving the user's original download, chat export, or invoice file. The service accepts resolved Paths and has no knowledge of SQLAlchemy, reimbursement entities, naming, or completeness.

`copy_file` validates that the source is a regular file, the destination parent already exists, and the destination does not exist. It creates a uniquely named temporary file inside the destination directory, streams content through `shutil.copyfileobj` with a bounded chunk size, flushes Python buffers, calls `os.fsync`, closes the handle, and compares the temporary size to the source size captured before copying. Only then does it rename the temporary file to the formal destination. Because temporary and final paths share a directory, the Windows rename is atomic within the filesystem. Any exception before publication removes the temporary file; cleanup failures propagate instead of being silently ignored.

Existing destinations are never overwritten. This protects managed attachments from stale indexes or concurrent user activity. `move_file` uses a same-filesystem rename, which is atomic and fits the planned `.trash` location under the archive root. A cross-volume MOVE reports the operating-system error rather than silently degrading into a partially recoverable copy/delete sequence; COPY remains the MVP default. `delete_file` only unlinks regular files and is not the Attachment deletion policy—Task 17 will move attachments to `.trash` instead.

Alternatives were rejected: copying directly to the final name exposes partial files, while placing temporary files in the system temp directory can make final rename cross-volume and non-atomic. Tests use `tmp_path` and cover Chinese paths, idempotent directory creation, default COPY semantics, atomic publish, fsync, no-overwrite behavior, missing parents and sources, simulated copy failure cleanup, MOVE, DELETE, and regular-file existence checks.
