# Repository Layer Design

Task 5 introduces five session-scoped repositories: Batch, Item, Template, Attachment, and MaterialType. A small private generic base implements identical create, get, list, update, and delete mechanics. It accepts an existing SQLAlchemy Session and flushes mutations without committing, following ADR-0002. Services will later compose several repositories inside one `DatabaseManager.transaction()` context. SQLAlchemy integrity errors remain visible to the service layer instead of being swallowed or translated prematurely.

Specialized repositories contain only persistence queries. `ItemRepository.search()` performs escaped substring matching across Item name, merchant, order number, and joined Batch name, then returns deterministic ID order. `AttachmentRepository` lists by Item, lists by the Item/material pair needed for attachment indexing, and searches hashes within one Item so identical files remain legal across different Items. MaterialType and Template add stable code/name lookups useful for initialization services. Repositories do not copy files, calculate completeness, create material requirements from templates, or contain UI behavior.

Tests use an isolated in-memory SQLite schema. Standard CRUD tests verify generated IDs, persistence, updates, deterministic listing, and deletion. Search tests cover all four required fields plus literal wildcard handling. Attachment tests verify Item/material filtering and Item-scoped hash lookup. A transaction-ownership test creates and flushes a record, rolls the caller's Session back, and proves the Repository did not commit. Existing database constraints continue to protect restricted deletes. This keeps Repository behavior narrow while preparing Tasks 6–8 to add seed and service logic safely.
