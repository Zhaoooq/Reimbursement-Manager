# Template Service Design

Task 7 introduces `TemplateService` as an application service constructed with `DatabaseManager`. Each public mutation opens one complete transaction and delegates persistence to `TemplateRepository` and `MaterialTypeRepository`, following ADR-0002. The service validates non-empty names and non-negative sort orders, resolves MaterialTypes by stable code, and raises explicit lookup or conflict errors rather than returning partially changed templates. Repository extensions provide eager Template loading and TemplateMaterial persistence without moving business rules into the database layer.

Template CRUD includes create, list, get, edit, and delete. Material operations add one unique material code, remove it, or change its required flag. When no sort order is provided, the service appends after the current highest order. Returned Templates eagerly load TemplateMaterials and their MaterialTypes so callers can inspect them after the transaction Session closes. File handling, Item creation, completeness, and UI behavior remain outside this service.

`ensure_default_template()` first invokes the idempotent default MaterialType initializer inside the same transaction. If “普通购物” does not exist, it creates the Template and four required TemplateMaterials—physical photo, payment screenshot, invoice, and order screenshot—in stable order. If the Template already exists, it returns the existing Template unchanged; startup must never undo a user's later changes. Database uniqueness still protects concurrent duplicate creation. Tests cover CRUD, detached eager reads, material add/remove/required changes, automatic ordering, explicit errors, default-template atomic content, repeated initialization, and preservation of user modifications. Existing Item requirements cannot be affected because the schema deliberately has no Template foreign key from Item; Task 8 will test the snapshot behavior when Items are created.
