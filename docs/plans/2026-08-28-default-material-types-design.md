# Default Material Types Design

Task 6 introduces one canonical tuple of six default MaterialType definitions. Each definition contains a stable lowercase code, an initial Chinese display name, and a short description. Business logic and future services will identify material types by code; names remain user-facing text and may be edited later. The catalog lives beside database initialization rather than inside UI or repository code.

Initialization receives an existing SQLAlchemy Session and follows ADR-0002 transaction ownership. It loads existing material types once, indexes them by code and name, then walks the defaults in deterministic order. A missing code creates and flushes one MaterialType through `MaterialTypeRepository`. An existing code is returned unchanged, preserving any user customization to its display name or description. Repeated calls—within one transaction or across application starts—therefore return the same records without duplicates.

Because names are also unique in the current schema, a default name occupied by a different code is an ambiguous data conflict rather than a harmless missing record. The initializer raises `DefaultMaterialTypeConflictError` with both codes. It does not catch or commit the error; `DatabaseManager.transaction()` rolls back any defaults created earlier in that attempt. Tests cover first creation, exact stable code/name mapping, deterministic order, repeated execution, preservation of customized existing data, name conflict rollback, and proof that the function does not commit independently. Wiring this initializer into final application startup requires a composition step that first guarantees Alembic migrations have run; that integration is intentionally deferred rather than making Task 6 depend on an unversioned `create_all()` call.
