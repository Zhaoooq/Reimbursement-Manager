# Attachment Service and Duplicate Detection Design

Tasks 13 and 14 introduce `AttachmentService.add_attachment(item_id, material_type_id, source_path)` as the application-level coordinator for importing one reimbursement file. The service is constructed with `DatabaseManager` and `StoragePathService`, with injectable `FileService`, `HashService`, and `NamingService` dependencies for deterministic testing. It supports common MVP image and PDF extensions, always copies the source, and never moves or modifies the user's original file.

One database transaction loads the Item together with its Batch, MaterialRequirements, and MaterialTypes. The requested MaterialType must belong to the Item's requirement snapshot, whether required or optional. The service calculates the source SHA256, queries `AttachmentRepository.find_by_hash(item_id, sha256)`, and raises `DuplicateAttachmentError` before creating directories or copying when the same content already belongs to that Item. The database constraint remains a concurrency backstop. Identical content is intentionally allowed for different Items.

The next material file index starts after the current database attachment count. NamingService receives the actual filenames already present in the Item directory, so untracked files also cause an index increment instead of an overwrite. StoragePathService produces the POSIX relative path for SQLite and the native destination Path. FileService creates the Item directory and atomically copies the source. The service then verifies destination existence and recalculates SHA256 from the copied target; a mismatch fails before database insertion. The Attachment row records the original name, generated name, relative path, normalized extension, copied size, source/target digest, and `AttachmentHealth.OK`.

Filesystem and SQLite cannot share a native transaction, so compensation is explicit. The outer operation records the destination only after FileService publishes it. Any later copy-verification, Repository flush, or transaction commit failure first rolls the database back through `DatabaseManager.transaction()`, then deletes the published file. If compensation itself fails, `AttachmentRollbackError` retains both failures rather than hiding either. Empty directories may remain and are harmless. Tests cover successful Chinese-path import, multiple files per material, same-Item duplicate rejection, cross-Item allowance, missing requirements, unsupported types, target-hash mismatch cleanup, and simulated database-write failure cleanup.
