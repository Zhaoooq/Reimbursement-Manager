# Database Session Layer Design

Task 2 will introduce an instance-based `DatabaseManager` rather than module-level engine or session globals. Each manager owns one SQLAlchemy `Engine` and one `sessionmaker`, so application services can receive database infrastructure explicitly and tests can create isolated managers. The UI will never receive or retain a global `Session`. File-backed construction accepts a `Path`, creates only its parent directory, and builds the SQLite URL through SQLAlchemy's `URL.create` API so Windows, spaces, and Chinese path components are handled without manual URL escaping.

The manager exposes a `transaction()` context manager as the preferred lifecycle boundary. Entering creates a fresh session; normal exit commits; an exception rolls back and is re-raised; final cleanup always closes the session. `expire_on_commit=False` keeps already-loaded scalar attributes usable after service transactions without leaving sessions open. The underlying session factory remains available for future repository integration, but ownership is explicit. `dispose()` releases engine resources when a test or the desktop application shuts down.

SQLite foreign-key enforcement is connection-local, so an engine connect listener will execute `PRAGMA foreign_keys=ON` for every connection. A separate `in_memory()` constructor will use `StaticPool` with `check_same_thread=False`, ensuring all sessions in one test manager observe the same temporary database. This test facility is intentionally limited to infrastructure verification and does not create application tables. Tests will cover Chinese file paths, connectivity, foreign-key configuration, distinct sessions, successful commit, rollback on error, shared in-memory behavior, and the existing full suite. Models and migrations remain Task 3 and Task 4 responsibilities.
